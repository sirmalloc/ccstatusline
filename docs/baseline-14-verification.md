# Baseline verification: N-session one-shot render benchmark (daemon epic #14)

Machine-readable results: `docs/baseline-14-results.json` (full per-run JSON,
including per-render latency arrays). Summary as generated by the harness is
reproduced below.

## What this is

The ONE-SHOT BASELINE for [axisrow/ccstatusline#14](https://github.com/axisrow/ccstatusline/issues/14):
what the current per-invocation model (one fresh `node dist/ccstatusline.js`
process per status-line repaint, as Claude Code invokes it today) costs at
1/10/36 concurrent sessions. The future daemon mode must beat these numbers;
the red line check is **aggregate CPU and aggregate RSS not above baseline**.

No daemon code exists in this branch; this is measurement only.

## How to reproduce

```bash
bun install && bun run build
python3 scripts/benchmark-render.py baseline \
    --runtime node --entry dist/ccstatusline.js --out /tmp/ccsl-baseline-14 \
    --max-load 10
```

`--self-test` covers percentile ranking, fixture generation and shim counting.
The harness refuses to start a scenario while 1-minute loadavg exceeds the
gate (default `cpu_count/2`; this run used `--max-load 10`) and stamps every
scenario with loadavg at the start/end of its measured phase. Legacy
single-run mode from the #397 work is unchanged:
`python3 scripts/benchmark-render.py <runtime> <entry> <label> [--width]`.

## Methodology

- **Scenarios**: {1, 10, 36} concurrent sessions x {cold, warm} x {small
  (500 rows, 0.62 MB), large (10000 rows, 11.5 MB)} transcripts = 12 timing
  scenarios + 12 instrumented count passes + 2 extra repeats of
  `s36-warm-small` (run-to-run variance). 26 runs total, 0 failed.
- **Cold**: fresh `HOME`/`CLAUDE_CONFIG_DIR`, measured render is each
  session's first (settings write, cold persistent caches). **Warm**: same
  fresh `HOME`, 2 warmup renders, then 6 measured renders per session
  (persistent git cache populated, steady state).
- Each scenario runs in a dedicated child interpreter, so
  `getrusage(RUSAGE_CHILDREN)` starts at zero: CPU user+sys covers the
  runtime process **and all reaped descendants** (git, sh).
- **Peak RSS**: `ru_maxrss` of the largest reaped child tree.
  **Aggregate RSS**: `ps` sampling (~25 ms cadence) of the live process tree,
  mean and max of sampled sums.
- **Latency**: wall time per render, nearest-rank p50/p95/p99.
- **Spawn counts**: separate instrumented passes with PATH shims for `git`
  and `security` (shim logs one line, then `exec`s the real binary). Shim
  overhead is why count-pass CPU/latency never enters the baseline tables.
- All sessions share one `HOME` per run (same-OS-user realism, as the daemon
  targets one user's sessions) and one dirty git repo as cwd (the default
  widget line renders `git-branch` + `git-changes`). Each session has its own
  transcript file and unique session_id. `CCSTATUSLINE_WIDTH=120`,
  `CCSL_FORK=1` (matches the production statusLine command).
- Output hash of every render is recorded; all runs produced exactly one
  distinct hash per scenario (deterministic rendering).

## How the daemon red line uses this

For a daemon prototype at N concurrent sessions, compare against the matching
baseline row: aggregate CPU-seconds per wall-minute and aggregate RSS (mean →
max) must not exceed the one-shot numbers. Example anchors from the warm table
at 36 sessions: **~207 CPU-s per wall-minute** (198.7 ms CPU per render at
~1040 renders/wall-min) and **~1.8–2.4 GB aggregate RSS** across ~36 concurrent
process trees with ~75–108 MB peak per process. The cold table bounds the
burst cost when all sessions repaint at once after a daemon restart.

## Noise and honesty notes

- Measured numbers only; no extrapolation from fewer sessions.
- Every render is a fresh process; the "warm" advantage comes only from OS
  page/disk caches and ccstatusline's own persistent caches (git cache TTL 5 s
  absorbs all git spawns in warm state — see spawn counts), which is exactly
  the one-shot steady state the daemon replaces.
- macOS page cache is not purged; "cold" means fresh HOME and first render,
  not cold disk.
- Aggregate RSS is sampled at `ps` granularity; very short-lived git children
  can be missed, so it undercounts. Peak RSS is exact (`ru_maxrss`).
- Spawn counts come from the instrumented passes only. Spawns via absolute
  paths (e.g. a runtime self-spawn for git-review refresh) are not
  shim-visible; the synthetic repo has no origin remote, so review-cache
  refresh does not trigger. In warm state the persistent git cache already
  absorbs git spawns (0.0/render), and cold counts *decrease* with session
  count (4.0 at 1 session → 1.5 at 36) because 36 concurrent first renders
  share one HOME's persistent cache — same-user realism, not an artifact.
- The machine was NOT idle: ambient loadavg oscillated ~8–40 during the run
  (sibling agent sessions rendering their own status lines and running
  builds). The gate held measurements out of the worst spikes; every scenario
  carries its own loadavg stamps in the JSON. Two rows (s36-warm-small,
  s36-warm-large) landed on spikes on the first pass and were re-measured;
  only those rows were replaced. Cross-load stability of the red-line metrics
  is empirically supported by the variance table (CPU/render 185–199 ms across
  loadavg 10–29) and by the counts-vs-timing agreement for identical
  scenarios. Latency percentiles carry the most load sensitivity; treat them
  as upper bounds for an idle machine.
- The harness sampler (a `ps` loop) adds a small constant measurement
  overhead, identical across scenarios, excluded from the CPU accounting by
  reaping order.
